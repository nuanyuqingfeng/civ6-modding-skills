# 工作史与决策记录（去项目化）

> 本文档只记录“规律、结论与教训”，不保留具体项目、人物、成品音频与本地路径。
> 作为本管线的演化依据，供后续维护者判断“为什么这样做”。

## 阶段一：搞清楚“冲突/覆盖”的本质

- 游戏音频引擎为 WWise，全部音频对象使用 32 位 ShortID。
- **事件（Event）ShortID = FNV-1(32) 对小写事件名哈希**：
  - 名字唯一 → 哈希唯一 → 事件不冲突；
  - 因此区分不同语音/音频 = 分配唯一事件名前缀，而不是用其它技法。
- **媒体/声音/动作/容器等其它 ID 为工程随机数值**：
  - 不同内容必须全域唯一，否则相同 ID 互相覆盖；
  - 完全相同的内容可共用同一 ID（无害去重）。
- **锚点容器与游戏同步对象禁止改号**：
  - 语音链路锚点、音乐 DummySwitches 等 `id\d+` 对象必须原样保留；
  - `Init.bnk` 承载游戏同步，mod 不自制/替换。

## 阶段二：工具化尝试

- 建立了 ID 注册表：扫描既有成品/模板工程，收集已用 ShortID，新分配时避让。
- 实现了两条打包路径：
  1. **纯 Python bank 重建**：解析模板 bnk 的 HIRC 字节布局，按 `BKHD + DIDX + DATA + HIRC` 重建；
  2. **Wwise 工程自动化**：复制模板工程、前缀改名、非锚点 ShortID 重排、一键生成。
- 纯 Python 路径最初用 ffmpeg 标准 MS ADPCM 内嵌，结构自检通过、事件哈希验证通过。

## 阶段三：游戏实机修正（关键转折）

- 在“普通音频”接入中，先只放文件、未注册加载动作 → 游戏内触发事件但无声。
- 定位到注册链路必须完整：
  - `Banks.ini` 写加载分类；
  - `.modinfo` 的 `<UpdateAudio>` 指向 ini；
  - 所有物理文件（bnk/txt/xml/ini/wem）必须进 `<Files>` 打包清单；
  - `.civ6proj`（ModBuddy 源工程）同步 `<UpdateAudio>` + `<Content>` 条目。
- 补充注册后仍发现实际播放异常，最终实机定位到**编码方案错误**：
  - WWise 的 “MS ADPCM” 是私有变体，ffmpeg 标准 `adpcm_ms` 并不兼容；
  - 直接用 ffmpeg 标准 ADPCM 内嵌进模板 bank，游戏按 WWise 私有格式解码 → **噪音 + 闪退**；
  - 且 ADPCM 压缩率约 25%，远不如成品音乐流式 Vorbis（约 8-10%）。
- 结论：**纯 Python ADPCM bank 不作为正式交付方案**。

## 阶段四：BGM 三组结构认知

- 明确文明音乐不是单一“bgm”类，而是三组：
  - 轮播背景音乐；
  - 外交背景音乐；
  - 主题音乐。
- 主题音乐建议按 4 个时代准备。
- 外交背景音乐采用官方标准做法：**一个文明对应一首外交背景音乐**，由 `LeaderMusic_<Civ>` 容器与 `Play_Leader_Music_<Civ>` 事件承载。
- `PauseModCivMusic` / `ResumeModCivMusic` 只用于临时遮挡场景，不能用于正常 BGM 时代切换或外交音乐切换，容易导致音乐停摆。

## 阶段五：响度均衡的三个坑（2026-09，实机复现）

背景：一批已交付 BGM 在实机被听出“忽大忽小”。逐文件测量追查后定位到三个彼此独立的坑，
**都与“积分 LUFS 达标”这个表象无关**。

1. **重复归一 = 纯风险**
   - 该批 97 个源文件里 **91 个本已精确落在目标**（-28.00 / -25.00）；重跑一遍均衡时所需
     增益为 0.00 dB，响度上毫无收益。
   - 而“被处理坏”的那 6 个文件，恰恰全部落在这 91 个之中。
   - 结论：均衡必须有**幂等判定**（目标 ±0.3 dB 内直接跳过），否则重跑只会制造损伤。

2. **`linear=true` 只是“允许”，不是“保证”**
   - ffmpeg `loudnorm` 在不满足线性判定时**静默**改走时变增益（泵浦），不报错、不告警。
   - 判据（`af_loudnorm.c` `init()`）：`(measured_tp + (target_i - measured_i) <= target_tp)`
     且 `(measured_lra <= target_lra)`；不满足即落到 `FIRST/INNER/FINAL_FRAME`。
   - 实证：6/6 个被时变增益处理过的文件，其源 LRA 全部 > 目标 LRA(11)；91 个线性处理过的
     文件全部 ≤ 11。用与流水线完全相同的命令重跑其中一个，产出与实机交付文件**逐字节一致**
     （MD5 相同），而该文件轨内增益在 3 秒窗上摆动达 5.95 dB。
   - 结论：**预检**该条件并拒写；处理后再读 ffmpeg 自报的 `normalization_type` 复核。
     注意 `--lra` 因此是双重身份——它同时是“是否允许线性”的开关。

3. **积分响度相等 ≠ 听感相等**
   - 同一批 97 首：积分响度极差仅 **3.10 dB**，但中位短时响度 S_p50 极差达 **7.60 dB**；
     `corr(LRA, S_p50 − I) = -0.555`（动态越大的曲子，典型听感越低于它自己的积分值）。
   - 更隐蔽的是**同池混排两档基准**：时代容器按轮播机制会把“本时代素材 + 上一时代素材”
     放进同一个列表，-28 与 -25 同容器即逐曲跳 3 dB 台阶（实测判出 低簇 n=24 中心 -28.00 /
     高簇 n=73 中心 -25.00 / 间隔 2.80 dB）。
   - 结论：轮播池改用**短时锚**（`--mode shortterm`，恒定增益路径）对齐听感；同一播放容器内
     严禁混排两档基准。

**验收教训**：只查“编码 / 采样率 / 声道 / 积分 LUFS ±1.5”的验收表**查不出泵浦**——被时变增益
处理过的文件积分精确 -25.00 LUFS，看不出任何异常。验收必须补 LRA 与同池短时响度离散度。

## 阶段六：`*.bak_*` 旁路备份的边界（2026-09 审查补记）

就地写类脚本会在原文件旁留一份 `.bak_*` 副本（`.bak_check` / `.bak_norm` / `.bak_ast` /
`.bak_wire` / `.bak_rebuild` / `.bak_reg` / `.bak_unreg`）。审查指出这与家族/工程「默认不建立
任何备份副本；git 可管理的文件，历史只交给 git」的口径**未对齐**。核实后的结论：

- **素材 / 母带 / 工程内部文件**上的副本（WAV、`.ast`、Wwise 工程 XML）属**有意例外**：
  这些文件不可再生或重做代价高，就地写坏需要可回退；副本不入库、不进交付包，验收后自行清理
  （与 SKILL.md §2.5「淘汰件与母带备份隔离」同口径）。
- **`.modinfo` / `.civ6proj`** 上的 `.bak_reg` / `.bak_unreg` 属**口径冲突**：这两个是 git 管理的
  项目主体文件，历史应由 git 承担；副本落在 Mods 副本里还会被工坊打包流程一并带走。
  → 处置：**不改脚本行为**（默认产出保持不变），改由文档明确「提交 / 交付前删除这两类副本」；
  若后续确需，再考虑给 `register_to_mod.py` / `unregister_audio.py` 加开关或把副本落到 `workspace/tmp/`。
- SKILL.md §3 的「`.bak_*` 口径」一段是本条的**唯一口径真源**，两处需同步改。

## 最终决策

- **正式音频交付统一走 Wwise Vorbis 流式**：
  - 在 Wwise 工程中把素材设为 Stream → 生成 Vorbis wem + bank；
  - 语音、普通音频、BGM 均按此路线。
- **保留且有效的部分**：
  - ShortID 规律（Event FNV-1、非 Event ID 避让、锚点保护）；
  - ID 注册表 `scan` 机制（防冲突基础）；
  - Wwise 工程自动化（复制/改名/重排/一键生成）；
  - 注册与校验流程（`register_to_mod.py --verify`）。
- **降级为实验/研究的部分**：
  - `audio_pack.py speechbank/plainbank` 纯 Python 生成，仅用于结构/ShortID 研究；
  - 它们不产出可交付的正式 bank。

## 留给后续维护者的检查单

1. 新音频接入先过素材核验与响度均衡，再进打包。
2. 打包前运行 `audio_pack.py scan` 刷新 ShortID 注册表。
3. 正式 bank 必须由 Wwise 生成 Vorbis（不要用纯 Python ADPCM 产物交付）。
4. 注册必须写齐 Banks.ini + UpdateAudio + Files/Content，并跑 `--verify`。
5. 命名坚持唯一前缀 + 槽位/用途；绝不改锚点对象。
6. 响度均衡前先确认源素材是否**本已在目标上**（幂等闸会跳过，别重复处理）；
   `--lra` 同时是“是否允许线性归一”的开关，源 LRA 超它会被静默降级为泵浦——
   脚本默认拒写该类文件并以退出码 2 报出，不要用 `--allow-dynamic` 掩盖。
7. 验收除积分 LUFS 外必须看 LRA 与同池短时响度离散度（`audio_check.py` 的 `[POOL]` 段）；
   同一播放容器内不得混排两档响度基准。
